EduSync.

Making a student dashboard easier to understand and try.

The student problem

EduSync began with my own frustration: course files, deadlines, announcements, and grades were spread across different views. The product idea was to make the next useful action easier to find. This is a personal observation, not a user-research finding.

The intended audience

Students balancing several courses and commitments, initially in a Brightspace/Microsoft university environment. The public experience also lets a recruiter evaluate the idea without a university account.

From feature inventory to a student benefit

Three design decisions

01 / Show value before asking for access

Make "Explore the demo" the primary action, with connection secondary. Visitors can try fictional tasks and grades before considering account access. The reasoning: show the product's value before asking for trust. Any effect on conversion remains untested.

02 / Give the day a starting point

Use a sage "Your next move" card, three summary counts, and separate navigation for detail. This gives the daily view a clear starting point. Completing a sample task advances the focus card and updates progress; reduced planning effort is a hypothesis, not a measured result.

03 / Make uncertainty visible

Place the final-score slider beside the projected grade, formula, and assumptions. Label it "A scenario, not a prediction." This makes the calculation easier to inspect and keeps an illustrative estimate from looking like an official university grade.

What was verified

Checked September 23, 2026: the demo loads without credentials, skips account lookup, and reads hard-coded fictional fixtures. Its controls use browser memory and contain no student-data or AI requests. Observed resources were static files only; signed-out course, grade, task, and announcement requests returned HTTP 401. The deployed demo bundle matched the reviewed build.

The demo shares the production domain; it is not a separate security sandbox. These checks establish the reviewed demo's behavior and signed-out access boundary, not a guarantee against every security flaw. Leaving the demo for student sign-in enters the separate authenticated flow.

My role & AI assistance

I defined the problem and project direction, reviewed iterations, and used Claude and Codex extensively for implementation, debugging, interface copy, and verification. The assistants generated substantial code; this is an AI-assisted product and messaging project.

Limitations

Live Brightspace access depends on expiring session cookies. Reliable current-semester importing and AI briefings remain unverified. Demo suggestions are scripted, task changes reset on reload, and grade scenarios simplify course rules. EduSync is independent and is not university-endorsed.

Outcome and next question

Delivered: a public landing page and interactive fictional-data demo. No formal user research, adoption, engagement, or time-saved results are claimed. Next: observe students finding a deadline and explaining a grade scenario to test clarity.
